# Agent 缺的不是下载器，是下载层

> 一个 Agent 在下载 3GB 模型权重时被打断了。它没有崩溃——它只是被 compaction 清掉了上下文。等它恢复过来，发现自己站在原地，而那 1.9GB 已经下载好的字节，躺在磁盘上，没人认识它们了。

这不是一个虚构的悲剧。这是 2026-11-27 真实发生在一个本地 Agent 会话里的事。它暴露的问题，比"下载慢"要根本得多：**我们一直在用给人设计的下载工具，服务一种根本不同的用户。**

---

## 一、人和 Agent，对"下载"的需求是两回事

我们熟悉的下载器——curl、wget、浏览器下载管理器——用户是人。整个交互模型建立在一系列关于人的假设上：

- 人会盯着进度条，失败了自己重试；
- 人会把文件"打开看看"，确认内容对不对；
- 人会读设置面板，调整并发数和镜像；
- 人的注意力是连续的，一个下载任务通常在一次会话里完成。

Agent 一条都不满足。

| 维度 | 人 | Agent |
|---|---|---|
| 存活周期 | 一次会话内连续运行 | 随时可能被杀（超时、compaction、预算耗尽） |
| 内容消费 | 下载完打开看 | **内容绝不能进 context** |
| 失败处理 | 看到错误，自己判断重试 | 需要结构化的、机器可读的错误 |
| 配置 | 能读设置面板 | 不会读设置，最好零配置 |
| 完整性 | 相信"下载完成" | 必须能在信任前重新校验 |

把这五种差异翻译成需求，会得到一份完全不同的规格书：

1. **状态必须落盘**——进程可能在任何一步死掉，进度不能只存在内存里；
2. **结果必须小**——返回的是一行元数据，不是文件内容；
3. **失败必须显式**——不能静默留下半成品，否则 Agent 会把坏文件当成好文件继续用；
4. **零配置**——镜像选择、并发数、后端选型都应该是自动的；
5. **可验证**——每个文件都要有可复查的摘要，信任之前能重哈希。

这不是"下载器的增强功能"。这是**另一类软件**：Agent 会话期间的文件 I/O 层。

---

## 二、什么是"下载层"

一个朴素的定义：

> 下载层是 Agent 与字节世界之间的接口。它把"我需要这份内容"翻译成"磁盘上有一个可验证的文件，这是它的路径、摘要和状态"，然后只把后者交给 Agent。

关键在 API 的形状。传统下载器的接口是：

```
download(url) -> 内容
```

下载层的接口是：

```
fetch(url, target, checksum?, mirrors?, resume?) -> 句柄{路径, 摘要, 状态, 警告}
```

内容从不经过 Agent 的上下文。Agent 拿到的是一个**句柄**——它知道文件在哪、多大、摘要是什么、是否来自缓存、是否真的续传了。之后所有操作都针对这个句柄：`verify` 重新校验，`read` 按需取几行，`manifest` 在会话重启后问"我之前都有什么"。

这个区别看起来小，实际是架构性的。它把下载从"一次性的 I/O 动作"变成了"有生命周期的文件管理"：

```
会话启动 → manifest → fetch → verify → read → 状态留在磁盘 → 下次会话可见
```

一旦你这样看，很多以前觉得"够用"的做法就不够用了。比如 `curl` 下载到目标路径——文件路径上可能出现不完整字节，Agent 无从分辨；比如 `webfetch`——它把内容压成有损投影送进 context，底层字节从未落盘，想问第二个问题就得把整页重新处理一遍。

## 三、四个设计原则

### 1. 状态是数据，不是内存

Agents 被杀是常态，不是异常。所以进度必须写到磁盘上，而且写的方式要能扛住崩溃：tmp 文件 + 原子 rename，确保任何时刻读到的都是完整状态，不会是写了一半的 JSON。

这里有个容易被忽略的细节：**进度快照和最终提交需要不同的持久化策略**。每 500ms 一次 fsync，在 1GB 下载上累计能花掉半秒纯等待——而这些中间状态丢掉其实无所谓，崩溃时最多回退一个快照。所以中间进度用无 fsync 的原子写，最终提交才 fsync。这是典型的"按数据的语义分层"，而不是一刀切。

### 2. 失败要显式，绝不留下半成品

一个下载器最危险的行为不是失败，是**看起来成功的坏文件**。

考虑这条真实路径：一个任务被中断，`.part` 文件留在磁盘上；后来签名 URL 刷新，任务 ID 变了，成了一个"新任务"；新任务启动时不认识那个 `.part`；aria2 带着 `--continue=true` 启动，把已有的字节当作"已经下载好的前缀"，直接续传。结果：一个混入旧字节甚至全零的文件被原子发布到目标路径，返回 `ok: true`。

Agent 拿到这个文件，无法分辨它是对的还是坏的——除非它自己有外部 digest。这就是为什么"失败要显式"不是口号，而是设计约束：

- 下载中的字节永远待在 `<target>.part`，目标路径只在校验通过后出现；
- 新任务启动时清理不属于它的残片；
- `resumed: true` 只在字节真的被复用时才报；
- 缓存文件校验失败时**改名**为 `.corrupt` 保留证据，而不是静默删除；
- 没有外部 checksum 时，明确返回 `integrity: "unverified"`——"我校验了传输和尺寸，但我不能证明这是源站的正确字节"。

最后一条尤其重要。它把一个隐含的谎言变成了一个显式的信任级别。Agent 可以选择接受，但至少不会被误导。

### 3. 内容永远不进 context

Agent 的上下文窗口是稀缺资源。一个 293KB 的网页直接塞进去，大约要吃掉 7 万个 token——一次就占掉 128k 窗口的一半以上。用 `webfetch` 之类的摘要工具看似省了 token，但拿到的是有损投影：底层字节从未落盘，想问页面的另一个问题，就得把整页重新处理一遍。

下载层把"获取"和"消费"彻底分开：

- `fetch` 把全量字节落到磁盘，context 里只回一个几百字节的 JSON；
- `read --grep` 按需取几行，带上下文，有硬上限，默认最多返回 256KB；
- Agent 想深挖时，直接对磁盘文件用 grep/python，而不是把文件倒进对话里。

实测：缓存一个 293KB 页面，首次消耗约 140 token（vs 约 73,000），二次查询按需约 1,000 token。这不是省一点，是量级差异——而且内容永久落盘、可校验、可离线复用。

### 4. 零配置，以及"默认诚实"

Agent 不会读设置面板。所以：

- 镜像自动探测：并行发 `Range: bytes=0-0` 请求，按可达性 > Range 支持 > TTFB 排序，主源中途失败自动切次优；
- 后端自动选型：优先纯 Go 实现（无子进程开销），外部下载器作为 fallback；
- 探测结果在 60 秒内复用——Agent 被杀后重调同一命令，不该再付一遍探测延迟。

但"零配置"不等于"沉默"。当 fallback 不可用、当 orphan 残片被丢弃、当缓存文件尺寸对不上，这些都要出现在 `warnings` 里。Agent 不读设置面板，但它可以读结构化警告。

## 四、真实案例：1.9GB 的教训

2026-11-27，一个 Agent 要下载 Qwen2.5-1.5B 的 3GB 模型权重。它踩中了三个坑，每一个都值得单独讲。

**第一坑：签名 URL 的身份。** 下载源是 `cas-bridge.xethub.hf.co` 的短效签名链接，约一小时过期。第一次用 native 后端，在 1.9GB 处 TLS 握手超时。重启后链接刷新，URL 里的 `Expires`、`Signature`、`X-Amz-*` 全变了——任务 ID 是按 URL 算的，于是刷新后的链接成了一个全新任务，那 1.9GB 进度没人认领。最后用 aria2 从头重下，花了 35 分钟。

**第二坑：并发粒度。** 文件大小 3GB，旧实现切成 16 个固定分片，每片约 193MB。一条慢连接就能拖住整个尾巴；续传的最小单位也是 193MB。

**第三坑：挂死。** 30 秒无数据超时挡不住"每几十秒滴几个字节"的连接——它会一直重置超时计时器，让任务挂上几个小时而不报错。

这三个坑的共同点是：**它们都不是"下载器不够快"，而是"下载层没有正确表达失败和恢复的语义"**。修复也对应三层：把签名参数从任务身份里剥离（并给无法识别的私有源提供 `--task-key`）；把固定分片改成 2–16MB 的工作单元 + 16 worker 队列；加一个 10 秒窗口、8KiB/s 的速率看门狗。

本地基准（256MB，单连接限速 1MB/s）：16.75 秒 → 4.40 秒，3.8 倍。但更重要的不是这个数字，而是**失败之后会发生什么**：现在它会在一个明确的位置停下来，告诉你为什么，并且下一次调用能从那里继续。

## 五、为什么是现在

Agent 正在从玩具走向生产。当 Agent 只跑 30 秒的 demo 时，`curl` 够用。当它要：

- 下载几 GB 的模型权重；
- 缓存大文档供后续多轮分析；
- 在一个可能被中断、被压缩、被重启的会话里持续工作；

"下载"就不再是一个动作，而是一段需要被管理的生命周期。

我认为未来每个 serious 的 Agent 运行时都会需要这样一层。它可能不是独立工具，而是被吸收进 agent 的文件系统抽象里。但无论形态如何，那套契约不会变：**状态落盘、失败显式、内容不进 context、信任可验证**。

OpenDrain 是这套契约的一个具体实现——纯 Go 标准库、零依赖、单二进制。但这篇文章真正想说的不是"用 OpenDrain"，而是：**如果你的 Agent 还在直接调 curl，你缺的不是一个更好的下载器，是一个下载层。**
